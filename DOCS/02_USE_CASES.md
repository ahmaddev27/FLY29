# UC-01: تسجيل الدخول إلى المنصة

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-01 |
| **الاسم** | تسجيل الدخول |
| **الفاعل الرئيسي** | Agent / Account Manager / Admin |
| **الأهداف** | الوصول الآمن للمنصة |
| **الأولوية** | عالية (P0) |
| **التكرار** | عدة مرات يوميًا لكل مستخدم |

### الشروط المسبقة (Preconditions)
- المستخدم لديه حساب نشط في النظام.
- اتصال إنترنت متاح.

### الشروط اللاحقة (Postconditions)
- **عند النجاح:** Session آمنة منشأة، توجيه لـ Dashboard المناسب.
- **عند الفشل:** المستخدم على صفحة تسجيل الدخول مع رسالة خطأ.

### السيناريو الرئيسي (Main Success Scenario)
1. المستخدم يفتح صفحة تسجيل الدخول.
2. النظام يعرض النموذج (بريد إلكتروني + كلمة مرور + reCAPTCHA).
3. المستخدم يدخل بياناته ويضغط "تسجيل الدخول".
4. النظام يتحقق من reCAPTCHA score (≥ 0.5).
5. النظام يبحث عن المستخدم في DB بالبريد الإلكتروني.
6. النظام يتحقق من كلمة المرور باستخدام `bcrypt::verify`.
7. النظام يتحقق من حالة الحساب (active).
8. النظام ينشئ Session/JWT بصلاحية 60 دقيقة.
9. النظام يسجل الحدث في `audit_log` (login_success).
10. النظام يوجه المستخدم لـ Dashboard المناسب لدوره.

### السيناريوهات البديلة (Alternative Flows)

**A1: حساب معلق**
- 7a. حالة الحساب = `suspended`.
- 7b. النظام يعرض: "حسابك معلق، تواصل مع الإدارة".
- 7c. لا تُنشأ Session. **انتهاء.**

**A2: كلمة مرور خاطئة**
- 6a. فشل التحقق من كلمة المرور.
- 6b. النظام يزيد `failed_attempts` للمستخدم.
- 6c. النظام يعرض رسالة خطأ عامة (لا يكشف ما الخطأ).
- 6d. **العودة إلى 1.**

**A3: تجاوز محاولات الفشل**
- 6e. `failed_attempts ≥ 5` خلال 15 دقيقة.
- 6f. النظام يحجب IP لمدة 15 دقيقة.
- 6g. إرسال بريد تنبيه للمستخدم.
- 6h. تسجيل الحادثة في `security_log`. **انتهاء.**

**A4: فشل reCAPTCHA**
- 4a. Score < 0.5.
- 4b. النظام يرفض الطلب بـ 403 Forbidden.
- 4c. تسجيل المحاولة كـ suspicious. **انتهاء.**

### الاستثناءات (Exceptions)
- **E1:** فشل اتصال DB → 500 Internal Server Error، رسالة عامة للمستخدم.
- **E2:** انتهاء صلاحية Session أثناء العملية → إعادة توجيه لصفحة الدخول.

### المتطلبات غير الوظيفية
- زمن الاستجابة: < 800ms في 95% من الحالات.
- توافق المتصفحات: Chrome, Safari, Edge, Firefox (آخر إصدارين).

# UC-02: عرض لوحة تحكم الوكيل

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-02 |
| **الاسم** | عرض Dashboard |
| **الفاعل الرئيسي** | Agent |
| **الأهداف** | مراجعة الرصيد والتصنيف والإحصاءات |

### الشروط المسبقة
- المستخدم مسجل دخول كـ Agent.

### السيناريو الرئيسي
1. الوكيل يدخل لـ `/dashboard` بعد تسجيل الدخول.
2. النظام يستعلم بشكل متوازٍ (Promise.all):
   - بيانات الوكيل الأساسية.
   - رصيد المحفظة النقدية.
   - رصيد محفظة الباكجات.
   - التصنيف الحالي + باقي الأيام.
   - إحصاءات الشهر الحالي.
3. النظام يحسب:
   - التقدم نحو المستوى التالي (`current_packages / next_tier_threshold`).
   - القيمة الدولارية = `points × point_value_usd`.
   - أقرب باكج مجاني يمكن استبداله.
4. النظام يعرض الواجهة بـ:
   - بطاقة التصنيف (مع شريط تقدم وعداد تنازلي).
   - بطاقتا المحفظة (مع أزرار الإجراءات).
   - ملخص الإحصاءات (4 KPIs).
5. النظام يحمّل الإشعارات غير المقروءة بشكل غير متزامن (Lazy).

### السيناريوهات البديلة

**A1: وكيل جديد بدون معاملات**
- 2a. جميع الأرصدة = 0.
- 3a. عرض رسالة Onboarding: "ابدأ بأول عملية بيع لكسب نقاطك الأولى".

**A2: وكيل قارب على التخفيض**
- 3b. باقي < 7 أيام والباكجات < العتبة.
- 3c. عرض Banner تحذيري بلون أحمر.

### المتطلبات غير الوظيفية
- Time-to-Interactive < 2 ثانية.
- Caching: بيانات Dashboard مع TTL = 60 ثانية (Redis).

# UC-03: استقبال معاملة من الموقع الرئيسي (Webhook Ingestion)

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-03 |
| **الاسم** | Ingest Transaction |
| **الفاعل الرئيسي** | Main 29FLY Site (System) |
| **الأهداف** | تحديث نقاط الوكيل تلقائيًا عند كل بيع |
| **الأهمية** | حرجة — العصب الرئيسي للنظام |

### الشروط المسبقة
- الموقع الرئيسي لديه `API_KEY` صحيح و `webhook_secret`.
- الوكيل المرسل `agent_id` موجود في DB.

### الشروط اللاحقة
- **عند النجاح:**
  - معاملة جديدة في `transactions`.
  - تحديث رصيد محفظتي الوكيل.
  - سجل في `points_history` مع config snapshot.
  - فحص ترقية التصنيف.
  - إرسال إشعار In-app.
  - 200 OK للموقع الرئيسي.

### السيناريو الرئيسي
1. الموقع الرئيسي يرسل `POST /api/v1/transactions/ingest`:
   ```json
   {
     "agent_id": "AGT-1234",
     "transaction_type": "package",
     "amount_usd": 1500.00,
     "destination": "Thailand",
     "transaction_date": "2026-11-01T10:30:00Z",
     "reference_id": "TXN-MAIN-998877"
   }
   ```
   Headers: `X-API-Key`, `X-Signature: sha256=...`.

2. النظام يتحقق من `X-API-Key` في DB (constant-time comparison).
3. النظام يحسب HMAC-SHA256(body) ويقارنه بـ `X-Signature`.
4. النظام يتحقق من Idempotency:
   - استعلام `transactions WHERE reference_id = ?`.
   - إذا موجود → return 200 `{ "status": "duplicate_ignored" }`.
5. النظام يتحقق من وجود `agent_id` وحالته (active).
6. النظام يبدأ DB Transaction:
   - 6a. يقرأ الإعدادات النشطة: `calculation_method`, tier-specific points, point_value.
   - 6b. يقرأ تصنيف الوكيل الحالي.
   - 6c. يحسب النقاط:
     - إذا `package_based` و `transaction_type=package`: نقاط = `tier.points_per_package`.
     - إذا `package_based` و `transaction_type=service`: نقاط = 1.
     - إذا `amount_based`: نقاط = `floor(amount_usd / tier.amount_per_point)`.
   - 6d. يُدرج في `transactions` مع snapshot للإعدادات.
   - 6e. يحدّث `cash_wallet_points` و `package_wallet_points` (نفس القيمة لكل محفظة).
   - 6f. يُدرج سجل في `points_history` لكل محفظة.
7. النظام يلتزم بـ Commit.
8. النظام يستدعي `TierEvaluationService::checkUpgrade(agent_id)` (Async عبر Queue).
9. النظام يستدعي `NotificationService::dispatch("points_earned", ...)` (Async).
10. النظام يُسجل الطلب في `api_logs`.
11. النظام يرد بـ:
    ```json
    {
      "status": "accepted",
      "transaction_id": "TXN-LOY-456789",
      "points_awarded": 4,
      "new_balance": { "cash": 1204, "package": 1204 }
    }
    ```

### السيناريوهات البديلة

**A1: API Key خاطئ**
- 2a. عدم تطابق.
- 2b. النظام يسجل المحاولة كـ unauthorized.
- 2c. إرجاع 401 Unauthorized. **انتهاء.**

**A2: Signature خاطئ**
- 3a. عدم تطابق HMAC.
- 3b. تسجيل كـ suspicious.
- 3c. إرجاع 401 Unauthorized. **انتهاء.**

**A3: Reference مكرر**
- 4a. الـ `reference_id` موجود.
- 4b. النظام يسجل في `api_logs` كـ `duplicate_ignored`.
- 4c. إرجاع 200 OK مع `status: duplicate_ignored`. **انتهاء (مقصودة).**

**A4: Agent غير موجود أو معلق**
- 5a. الوكيل غير موجود → 404.
- 5b. الوكيل معلق → 422 مع `{ "error": "agent_suspended", "transaction_held": true }`.
- 5c. حفظ المعاملة في `pending_transactions` للمعالجة عند إلغاء التعليق.

**A5: فشل DB أثناء Transaction**
- 6g. الـ Transaction يُلغى (Rollback).
- 6h. النظام يضيف المهمة إلى `failed_jobs` queue.
- 6i. إرجاع 500 (يُحفّز Retry من الموقع الرئيسي).

### الاستثناءات
- **E1:** Payload schema غير صالح → 422 Validation Error مع تفاصيل.
- **E2:** Rate Limit (> 100 req/min من نفس API key) → 429 Too Many Requests.

### المتطلبات غير الوظيفية
- زمن الاستجابة: < 300ms (p95).
- معدل النجاح: ≥ 99.9%.
- Throughput: ≥ 100 req/sec.

# UC-04: الترقية الآلية للتصنيف

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-04 |
| **الفاعل الرئيسي** | System (TierEvaluationService) |
| **المحفزات** | بعد كل UC-03 ناجح |

### الشروط المسبقة
- معاملة جديدة سُجّلت للوكيل.

### السيناريو الرئيسي
1. الخدمة تُستدعى مع `agent_id`.
2. تقرأ التصنيف الحالي للوكيل.
3. تحسب عدد الباكجات المباعة في النافذة الحالية:
   - **calendar_month:** من 1 الشهر حتى الآن.
   - **rolling_30_days:** آخر 30 يومًا (إن مفعّل).
4. تقرأ عتبات التصنيف من `system_settings`.
5. تحدد المستوى المستحق (أعلى مستوى تتجاوز عتبته).
6. إذا المستوى المستحق > التصنيف الحالي:
   - 6a. تحديث `agents.current_tier`.
   - 6b. تحديث `agents.tier_valid_until = NOW() + 30 days`.
   - 6c. إدراج سجل في `tier_history` (action=upgrade).
   - 6d. إرسال إشعار "ترقية" (UC-14).
   - 6e. تخصيص Account Manager (إذا كان المستوى الجديد يستحق Manager خاص).
7. إذا المستوى المستحق = التصنيف الحالي:
   - 7a. تمديد `tier_valid_until = NOW() + 30 days` (تجديد).
8. إذا المستوى المستحق < التصنيف الحالي:
   - **لا إجراء فوري** — التخفيض يتم فقط عبر Cron (UC-05) عند انتهاء النافذة.

### الاستثناءات
- **E1:** فشل قراءة الإعدادات → سجل خطأ، عدم تنفيذ، إشعار للأدمن.

# UC-05: التخفيض الآلي للتصنيف (Cron Job)

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-05 |
| **الفاعل الرئيسي** | System (Daily Cron) |
| **التوقيت** | 02:00 يوميًا بتوقيت Asia/Riyadh |

### الشروط المسبقة
- موعد التشغيل اليومي حلّ.

### السيناريو الرئيسي
1. الـ Cron يبدأ.
2. النظام يستعلم: `agents WHERE tier_valid_until <= NOW() AND current_tier != 'bronze'`.
3. لكل وكيل في النتيجة:
   - 3a. حساب الباكجات في النافذة (calendar_month أو rolling).
   - 3b. تحديد المستوى المستحق وفق الباكجات.
   - 3c. إذا المستحق < الحالي:
     - تحديث `current_tier` إلى المستوى الجديد.
     - تحديث `tier_valid_until = NOW() + 30 days`.
     - إدراج في `tier_history` (action=downgrade).
     - إرسال إشعار "تخفيض" (UC-14).
   - 3d. إذا المستحق = الحالي: تجديد `tier_valid_until` فقط.
4. النظام يُولّد تقريرًا يوميًا للأدمن (ملخص الترقيات/التخفيضات).
5. النظام يستعلم بشكل منفصل عن الوكلاء المهددين بالتخفيض في 7 أيام:
   - `tier_valid_until BETWEEN NOW() AND NOW() + 7 days`.
   - الباكجات الحالية < العتبة الحالية.
   - إرسال "تحذير ما قبل التخفيض" (UC-14).

### السيناريوهات البديلة

**A1: فشل تنفيذ لوكيل معين**
- 3e. خطأ في معالجة وكيل واحد.
- 3f. تسجيل الخطأ + الاستمرار للوكيل التالي (لا إيقاف الـ Job).
- 3g. تقرير نهائي يشمل قائمة الإخفاقات.

### المتطلبات غير الوظيفية
- المهمة يجب أن تنتهي خلال 30 دقيقة لـ 10,000 وكيل.
- استخدام Chunking (100 وكيل/دفعة).

# UC-06: طلب تحويل النقاط لرصيد نقدي

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-06 |
| **الفاعل الرئيسي** | Agent |

### الشروط المسبقة
- وكيل مسجل دخول.
- رصيد المحفظة الأولى ≥ 800 نقطة (الحد الأدنى).

### السيناريو الرئيسي
1. الوكيل يفتح صفحة "تحويل النقاط".
2. النظام يعرض:
   - الرصيد الحالي.
   - حقل إدخال (Slider + Number input).
   - حاسبة فورية: `points × point_value_usd = $X`.
3. الوكيل يدخل العدد (مثلاً 1000).
4. النظام يتحقق محليًا: ≥ 800 وضمن الرصيد المتاح.
5. الوكيل يضغط "تقديم الطلب".
6. النظام يعرض Modal تأكيد.
7. الوكيل يؤكد.
8. النظام يبدأ DB Transaction:
   - 8a. التحقق مجددًا من الرصيد (race condition prevention).
   - 8b. إنشاء سجل في `redemption_requests` (type=cash, status=pending).
   - 8c. حجز النقاط: `available_points -= 1000`, `locked_points += 1000` في `cash_wallet_points`.
   - 8d. سجل في `points_history`.
9. Commit.
10. إرسال إشعار للأدمن (UC-14).
11. عرض رسالة نجاح للوكيل + توجيه لصفحة "طلباتي".

### السيناريوهات البديلة

**A1: عدد أقل من الحد الأدنى**
- 4a. < 800.
- 4b. إظهار خطأ Inline. **العودة لـ 3.**

**A2: عدد أكبر من الرصيد**
- 4c. > available_points.
- 4d. إظهار خطأ. **العودة لـ 3.**

**A3: Race condition (سحب متزامن)**
- 8a-i. الرصيد غير كافٍ عند Re-check.
- 8a-ii. Rollback.
- 8a-iii. عرض خطأ "تغير الرصيد، حاول مجددًا".

# UC-07: استبدال نقاط بباكج مجاني

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-07 |
| **الفاعل الرئيسي** | Agent |

### الشروط المسبقة
- وكيل مسجل دخول.
- رصيد محفظة الباكجات ≥ تكلفة الباكج المختار.

### السيناريو الرئيسي
1. الوكيل يفتح صفحة "الباكجات المجانية".
2. النظام يعرض الباكجات النشطة من `free_packages`.
3. الوكيل يختار باكجًا (مثلاً تايلاند - 1000 نقطة).
4. النظام يعرض Modal: تفاصيل الباكج + تأكيد.
5. الوكيل يؤكد.
6. DB Transaction:
   - 6a. التحقق من الرصيد.
   - 6b. إنشاء `redemption_requests` (type=package, package_id=X, status=approved).
   - 6c. خصم النقاط نهائيًا من `package_wallet_points`.
   - 6d. سجل في `points_history`.
7. Commit.
8. إرسال إشعار للأدمن لإتمام الإجراءات اللوجستية (UC-14).
9. عرض رسالة نجاح: "تم! سيتواصل معك مدير حسابك خلال 48 ساعة لتنسيق التفاصيل".

### السيناريوهات البديلة

**A1: الباكج تم تعطيله بين العرض والتأكيد**
- 6a. الباكج `is_active = false`.
- 6b. Rollback. عرض: "الباكج لم يعد متاحًا".

# UC-11: الموافقة/الرفض على طلبات التحويل

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-11 |
| **الفاعل الرئيسي** | Admin |

### السيناريو الرئيسي - الموافقة
1. الأدمن يفتح "الطلبات المعلقة".
2. يختار طلبًا.
3. يراجع: الوكيل، تاريخ الطلب، النقاط، القيمة بالدولار.
4. يضغط "موافقة".
5. Modal تأكيد.
6. DB Transaction:
   - 6a. تحديث `redemption_requests.status = 'approved'`.

7. Commit.
8. إشعار للوكيل (UC-14).
9. (خارج النظام) المدير يحوّل المبلغ عبر القناة المالية.

1-3. نفس الخطوات.
4. يضغط "رفض".
5. Modal يطلب سببًا (نصي إجباري).
6. DB Transaction:
   - 6a. تحديث `status = 'rejected'`, `rejection_reason = ...`.
   - 6b. فك الحجز: `available_points += 1000`, `locked_points -= 1000`.
7. Commit.
8. إشعار للوكيل مع السبب.

# UC-12: التعديل اليدوي للنقاط

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-12 |
| **الفاعل الرئيسي** | Admin |

### السيناريو الرئيسي
1. الأدمن يفتح ملف الوكيل.
2. يضغط "تعديل نقاط".
3. نموذج: المحفظة، إضافة/خصم، العدد، السبب (إجباري).
4. يضغط "تنفيذ".
5. النظام يتحقق:
   - **إذا العدد > 500:** يتطلب موافقة مدير ثانٍ (Dual Approval).
     - 5a. إنشاء سجل في `pending_adjustments`.
     - 5b. إشعار لمديرين آخرين.
     - 5c. عند موافقة الثاني، يُنفذ.
   - **إذا ≤ 500:** تنفيذ مباشر.
6. التنفيذ:
   - تحديث رصيد المحفظة.
   - سجل في `points_history` بـ source=manual_adjustment.
   - سجل في `audit_log` (الأدمن، السبب، القيم).
7. إشعار بريدي للوكيل (إضافة فقط، الخصم لا يُنبَّه عليه افتراضيًا).

# UC-14: إرسال إشعار

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-14 |
| **الفاعل الرئيسي** | System (NotificationService) |

### السيناريو الرئيسي
1. حدث يُحفّز إشعارًا (ترقية، استبدال، إلخ).
2. الخدمة تستقبل: المستلم، نوع الإشعار، البيانات.
3. تستعلم عن تفضيلات المستلم (`user_notification_preferences`).
4. تحدد القنوات النشطة (In-app / Email / SMS).
5. لكل قناة:
   - 5a. إنشاء job في Queue (channel-specific).
   - 5b. Worker يعالج:
     - In-app: إدراج في `notifications`.
     - Email: استدعاء SMTP (Mailable).
     - SMS: استدعاء Twilio/Provider.
6. تسجيل النتيجة في `notification_log`.

### السيناريوهات البديلة

**A1: فشل إرسال**
- 5c. الـ provider يفشل.
- 5d. Retry ثلاث مرات بـ Exponential Backoff.
- 5e. بعد الفشل النهائي: تسجيل في `failed_notifications` + إشعار للأدمن.

# UC-15: مهمة المطابقة اليومية (Reconciliation)

| الحقل | القيمة |
|-------|--------|
| **المعرف** | UC-15 |
| **الفاعل الرئيسي** | System (Daily Cron) |
| **التوقيت** | 03:00 يوميًا |
| **الفئة** | [تحسين مقترح] |

### السيناريو الرئيسي
1. الـ Cron يبدأ.
2. النظام يطلب من Main Site API: ملخص اليوم السابق:
   ```
   GET /api/v1/transactions/summary?date=2026-11-10
   → { "count": 1234, "total_amount": 456789.50 }
   ```
3. النظام يحسب نفس المؤشرات من `transactions`:
   ```sql
   SELECT COUNT(*), SUM(amount_usd) FROM transactions WHERE DATE(created_at) = ?
   ```
4. مقارنة النتائج.
5. **إذا متطابق:** تسجيل نجاح، انتهاء.
6. **إذا اختلاف:**
   - 6a. النظام يطلب القائمة الكاملة من Main Site.
   - 6b. مقارنة `reference_id` لكل معاملة.
   - 6c. تحديد المفقود في نظام الولاء.
   - 6d. إعادة معالجة كل معاملة مفقودة (استدعاء UC-03 برمجيًا).
   - 6e. تقرير "Discrepancy Report" مفصّل للأدمن.
